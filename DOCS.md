## Product model

OwnDashboard is an own-only professional operating system. The main entities form a connected graph:

```text
Organization ─┬─ Opportunities ── won conversion ── Project
              ├─ Projects
              └─ Invoices

Project ──────┬─ Tasks          Opportunity ── Tasks / Notes / Prompts
              ├─ Notes
              ├─ Client communication
              ├─ Costs / Crons
              ├─ Transactions / Subscriptions / Invoices
              ├─ Dates / Prompts
              └─ Library links (project_links: uses | reference | tool)

Prompt ── Library links (prompt_links)
Tool ── one library link ── Projects (project_links, role tool)
     └─ optional Subscription (monthly cost)

Inbox item ── confirmed routing ── Task | Note | Opportunity | Project
                                  Organization | Job application | Date
                                  Transaction category
```

These are real foreign-key relationships. RLS policies verify that every referenced organization, project, opportunity, invoice, or job application belongs to the authenticated user.

## Application architecture

`src/app/[[...slug]]/page.tsx` is the authenticated server boundary. It:

- validates a canonical or supported legacy route;
- redirects meaningful legacy bookmarks;
- checks the user with `auth.getUser()`;
- loads own-scoped Supabase rows and Google Calendar windows in parallel;
- performs no profile upsert or other rendering side effect;
- seeds `DashboardShell` with server data.

`src/components/dashboard-shell.tsx` keeps the existing single-shell architecture. Entity state is stored in the shared TanStack Query cache through `useEntityStore`, so existing high-value panels remain controlled and cache invalidation stays centralized.

Failed initial reads render a retry state before editable panels mount; verified cached records remain available during background failures. Destination panels load on demand while preserving server rendering and shell state. Public tour data lives in a separate query cache and cannot reach live APIs, Supabase, exports, sign-out or OAuth linking. Fixture entity stores never refetch live records. Dev-preview retains its production 404 guard and also isolates real backend configurations; only the nonexistent E2E backend permits mocked mutation requests.

The server-rendered shell is visibly busy and inert until its client handlers hydrate; its layout and persistent destination state stay mounted. The shell switches canonical routes with the History API for an SPA feel. Browser back/forward is synchronized through `popstate`. The sidebar, mobile navigation, keyboard chords, and command palette all use the same `NavTab` source of truth. The contiguous `g`, `g` chord opens Goals and `g`, `h` opens Home. Prefixes expire after 1.5 monotonic seconds and clear on other/ignored keys or focus changes; editable fields, modal/select/menu widgets, IME and already handled or modified events keep their own keys. Project detail is the one supported nested route: `/projects/[id-or-slug]`. The authenticated server boundary resolves it only against the current user's loaded projects; unknown or cross-user identifiers return 404.

## Hubs

### Home

Home shows the daily operating context: calendar, deadlines, opportunity follow-ups, recurring spend, active projects, and configurable widgets. Its task surface transactionally snapshots up to seven open tasks each day, ordered by priority and randomized within priority bands. GLOBAL tasks are database-enforced priority 6. Completing all seven marks that professional workday in a 49-day GitHub-style completion garden; this is task execution history, not the retired lifestyle streak feature.

Recurring goals use local calendar periods. Biweekly windows share the Monday 1 January 2024 anchor and remain stable across daylight-saving changes; the next period starts at its exclusive local-midnight end.

### Inbox

Inbox and References are hidden from every navigation surface (`HIDDEN_NAV_TABS` in `src/lib/nav-tabs.ts`): the sidebar, the mobile bar and More sheet, the command palette, the `g` chords, Settings and Home widgets. Their routes still render at `/inbox` and `/references` with a short note, and their tables, RPCs and exports are unchanged. Notifications load only on the Inbox route; there is no sidebar bell.

Inbox is a triage queue, not a second task list. Manual captures and integration events land as `inbox_items`; notification records are visible in the same action center. Notifications support safe source links, mark-read, snooze, and dismiss actions. Inbox search, source/status/destination filters, snooze, dismiss, restore, source links, and bulk dismiss support deliberate triage. A user chooses the destination and clicks Process; only then does the `route_inbox_item` `SECURITY INVOKER` RPC create or update the destination and mark the item processed in one transaction. Retries return the recorded route instead of creating duplicates. Valid relationship identifiers in an item's payload are carried into routed records and are rechecked by RLS.

### Work

Work overview summarizes active projects, open opportunities, due follow-ups, issued invoices, explainable project-health warnings, and the current week's planning. Health is a transparent heuristic based on on-hold status, overdue linked tasks, disabled crons, crons that stopped reporting a successful run, and costs without recorded revenue.

Recent GitHub history is read on demand with a one-minute query cache. A project shows up to 15 commits; Work reads five per distinct repository among the ten most recently updated active linked projects, using at most four concurrent requests. Work discloses capped project scope and unavailable repositories, while a wholly failed read is an error. Missing access is distinct from empty history. Failed refreshes retain confirmed data with Retry. Optional code-volume statistics have a separate three-second limit and no polling; the label reflects the returned one-to-four-week window. The public preview does not request live history.

Projects use a sortable summary table with a dedicated non-text drag handle. `projects.engagement` separates the owner's own products (`own`) from freelance work the owner was hired for (`client`); the table and the sidebar list own projects first, then a hairline "Freelance" divider and the client projects. Settings → Active projects gives every active project an Own/Freelance control that writes `engagement` through the owner's session, so the sidebar, the table and the Money split regroup the project at once, without a reload. Reordering works within a group while `sort_order` stays one sequence. The code-level portfolio registry (`src/lib/portfolio.ts`) materializes the daily projects without GitHub and binds each row by `projects.portfolio_key`; a venture subsection (Design Lab, GoVIRAL) is a child row through `projects.parent_id`, listed under its parent without a drag handle. The registry never renames a row or changes its engagement. Competition reads a complete, strictly validated owner-stamped snapshot through the route loader and owner-scoped lazy query; both editor surfaces use stable creation retries, captured-version writes, guarded drafts and explicit cached-refresh recovery in the audit branch. Confirmed row changes update the owner cache without an immediate whole-list download; a prior failed collection refresh stays visible until a successful complete read. Both Competition views page complete data locally in groups of 50. Search indexes the complete snapshot, and missing cached project details retain the research in an unavailable-project group. Competition (`competitors`) is its own destination, documented in [Portfolio, Competition and development finance](docs/portfolio-competition-finance.md); it marks research whose review date is missing or 90 days old or older as needing a refresh and can filter the list down to exactly those rows. Each project has a canonical workspace with Overview, Tasks, Activity, Communication, Repository, Finance, Competition, Knowledge, Scaling and Monetization tabs. Overview lists the library links the project uses (`project_links`), each with a role and a note on how it helps, added through the shared library picker. Knowledge lists every prompt by kind and copies it with this project filled in.

Projects match GitHub repositories by the numeric repository id (`projects.repo_id`) and fall back to the current or a previous name (`previous_repo_full_names`). The chart and allocation tables disclose that historical estimates reuse current prices/shares.

### Money

CSV import accepts files up to 2 MiB/5,000 transactions, validates dates, supported static-FX currencies, two-decimal amounts and payment symbols, and preserves quoted multiline notes. New imports use SHA-256 source/occurrence identities. Verified legacy imports are skipped; conflicting legacy fields require review at the stated source row. Confirmed 250-row batches can be retried after a partial failure without reinserting their strong keys. The file remains available after failure, and unavailable classification rules block import. Without a bank-provided id, overlap between partial exports of identical payments cannot be proven automatically. CSV uses `import_transaction_batch`; bank sync uses its service-only `import_bank_transaction_batch` wrapper with account-scoped SHA-256 identities and same-account legacy recognition. Both retain the predicate required by the existing partial unique index. It validates an explicit field allowlist, precision, dates, supported currency and related ownership; returns confirmed inserted ids; and leaves existing rows untouched. Bank sync retains its cursor after failed batches or unconfirmed status writes, replays confirmed identities safely, preserves an existing balance when the provider omits it, refuses a currency change without a new evidenced balance, skips unchanged balance writes and refuses to invent a new opening balance or account currency. Manual sync validates bounded explicit input and rate-limits pulls; malformed input cannot widen to all banks. Manual and scheduled passes require complete connection reads and report partial/consent failures honestly. A failed scheduled pass does not send a success heartbeat. Connection controls prevent overlapping actions and expose safe inline failure/retry states. The bank list requires a complete exact count with explicit retry and a 15-second read bound. Disconnect verifies an owned/versioned receipt and reports upstream revocation separately; imported financial rows remain untouched.

Manual and scheduled bank processing share one 40-second asynchronous budget, after manual auth/input/rate checks, within a 60-second function limit. Provider requests, credential/ledger reads and database retry waits receive that signal; a late receipt cannot continue a failed pass or advance its cursor. Unprocessed connections count as failures and suppress the success heartbeat. Completed batches remain safe to retry. Rule evaluation in bank, CSV and retroactive application is bounded before writes; CSV retains the file and explains an excessive-work refusal. The timer is not a synchronous CPU benchmark or a provider billing cap.

Transaction rules replace the old single-keyword auto-categories. A rule is a list of conditions — description, account, amount, date or direction, compared with is, contains, does not contain, a regular expression, one-of, a threshold or a range — and a set of actions that write the category, project, subscription or description. Rules run in three stages (before, default, after) and inside a stage the broadest rule runs first, so a narrower rule overwrites it; `src/lib/transaction-rules.ts` is the whole engine and is shared by every bank sync, the CSV import, the editor and the apply route, so a transaction is filed the same way whichever path it arrives on. There is no payee column: the bank's merchant and remittance text lands in `transactions.note`, and a rule about a merchant is a rule about the description. The editor shows two counts and labels both — how many of the loaded transactions a rule matches, and, on request, a full count from `POST /api/money/rules/apply`, which pages through the owner's whole ledger with their own session and can also apply the rule retroactively. A rule action naming a project or subscription the owner does not own is dropped before the write, because the transactions policies verify each relationship. The editor makes each action explicit: unchecked fields remain unchanged and a selected empty field clears its value. Editing preserves existing clear actions; failed or stale saves retain the draft. Updates, toggles and deletions check the captured `updated_at` and a returned row; new-rule retries reuse one UUID without overwriting an existing record. Counts refer to the checked draft and disappear after its conditions/actions change. Batch evaluation prepares rule order and ownership once. CSV and bank sync read complete rules and parent ids through one `transaction_rule_context` aggregate, refusing capped or malformed results instead of silently losing ownership ids. It permits up to 1,000 rules, 10,000 project ids, 20,000 subscription ids and 4 MiB, under invoker rights; service sync names its verified owner explicitly. Pattern conditions use case-insensitive RE2 matching through pinned `re2js` 2.9.0, with a 200-character bound and a 32-pattern LRU. Unsupported lookarounds/backreferences refuse the whole rule; matching never falls back to native JavaScript backtracking. Shared fetchers import the engine only for the Finance rule read. Legacy `transaction_category_rules` rows are copied into the new table by the migration; the old table is kept as the rollback path and stays in the financial export.

Incoming bank payments are paired with issued invoices deterministically. `src/lib/payment-matching.ts` is the whole rule: the payment's variable symbol has to name exactly one issued bank invoice, the currencies have to be identical, and the amount has to sit inside that invoice's own rounding tolerance — a crown on a CZK invoice with `round_total`, because that is what `computeTotals` rounds to, and a cent everywhere else. Nothing here calls a model. A pair sets `transactions.invoice_id`, `matched_at` and `match_source`, and marks the invoice paid on the day the money arrived rather than the day the matcher ran. Everything else stays in the **Unmatched payments** card on the Money child routes, each leftover labelled with its reason: no variable symbol, no invoice with that symbol, a different currency, an amount that does not match, an invoice that is already paid, or two open invoices sharing one symbol. The card links a leftover by hand through `POST /api/money/payment-match`, which runs with the owner's own session so the transactions update policy verifies the invoice's owner. The same matcher runs unattended from `/api/cron/payment-match`; it is idempotent, because a linked payment carries `invoice_id` and is no longer a candidate. The variable symbol itself is captured at ingest — from the provider's structured reference or remittance text — GoCardless's PSD2 fields, Fio's own VS column — and from a `Variabilní symbol` column on an imported statement — with a note fallback for rows synced before the column existed. The invoice list names the payment that settled each paid invoice.

Bank sync is one adapter per provider behind a single interface. `src/lib/bank/provider.ts` is the contract — consent status and expiry, accounts, transactions since a cursor, revoke — and `src/lib/bank/registry.ts` is the only place anything asks whether bank sync is usable, so a deployment configured for one provider is not blocked by another being unset. GoCardless Bank Account Data, Fio banka's token API and Enable Banking are the registered providers; a `bank_connections.provider` value outside that set throws instead of being treated as GoCardless, and the database carries the same check. GoCardless is an app-level secret pair; a Fio token belongs to one person and is stored in the service-role-only `bank_provider_credentials` table, written through `POST /api/bank/credentials` and never returned by any endpoint, including `/api/integrations/status`. Enable Banking is registered and signs the RS256 assertion its API expects, but reports itself as not set up and refuses every data call until an application id and RSA key pair exist and its flow has been verified. Each provider namespaces the keys it writes — Fio uses `fio:` on both `accounts.external_ref` and `transactions.external_id`, GoCardless keeps its refs bare so existing rows still match — so re-syncing stays idempotent across providers. Consent expiry is modelled rather than inferred: `consent_expires_at` is stored whenever the provider states one, the bank card shows it beside the status, and `/api/cron/bank-sync` marks a lapsed connection expired before it pulls anything. Each connection also has its own sync trigger, `POST /api/bank/sync` with a `connectionId`, beside the existing sync-everything button.

Finance transaction defaults refresh when a new form opens and retain an explicitly chosen date. Monthly chart windows follow the shared browser clock; the clock refreshes immediately when a mounted tab regains focus. Failed account edits keep their draft fields and report the rollback. Account deletion invalidates related transactions after foreign-key updates.

IG TIPS (`/ig-tips`, after Links in Library) holds the library's idea records (`ai_links.record_type = 'idea'`): practical tips saved from Instagram Reels and from research. Tips are grouped by topic (`ai_links.tip_group`: content ideas, formats and editing, platforms and reach, growth and retention, pricing and monetization, research and testing, design and web, AI cost, quality and safety, operations and career; no group reads Ungrouped) in the fixed order of `TIP_GROUPS` in `src/lib/ig-tips.ts`. Details keeps the research notes, why it is useful with its score, the projects that benefit, the sources and "Add to project". Search matches every word across the title, summary, notes, why it is useful, the projects that benefit and the topic name, ignoring case and accents; topic chips narrow it to one group. The tip dialog writes the title, original URL, topic, summary and notes; a new tip has no category and no pricing. The data loads through the same `aiLinks`, `aiCategories`, `projectLinks` and `projects` keys as Links, so the two sections share one cache and one set of own-only policies. The IG TIPS export is `version: 5` (#90): it selects all tips, chosen topics or chosen tips, groups by topic, has no price filter and names each tip's topic and card text `tip_group` and `tip_summary`.

IG TIPS and the marketing calendars close the loop in both directions (#91).
