# Application UX audit

Reviewed 23 October 2026 against `d6f60c7`. Evidence uses the real application in `/dev-preview` with synthetic fixtures. Screenshots show current components; the HTML's proposed components are labelled separately. No Production design change has been applied.

## Design decision

Keep the centered application shell and semantic visual system. Give each destination one visible title, one clear primary action and a content width suited to its task. Align comparable cards, rows and controls through shared primitives. Let short desktop forms use one row; let mobile wrap with 44 px targets. Equal card heights make sense for peer metrics and resource cards, but stretching an attention list to the height of a separate planner produces empty space.

## Responsive and accessibility evidence

- DNESKAi source/mix layout inspected at 430, 768, 1024 and 1728 px; editor/topics at 360 and 1440 px. Captures include measured document width; these pages did not show document-level horizontal overflow. This does not prove every nested scroller or dialog is correct.
- Home, Work, Transactions, Invoices, Tasks, Notes, Career and Settings additionally captured at 360 px. Main desktop destination captures use 1440 × 900. English/light and Czech/dark were inspected, plus selected Czech/light screens. This is sampled parity coverage, not every screen in all four combinations.
- Browser interactions exercised unsaved draft loss, source/mix navigation, Career's fixture refresh, mobile More keyboard wrap/Escape and command palette Escape. Existing fixture states show empty, disabled, failed, disconnected and pending work. Offline, permission/reauthorization and slow loading were traced in source/tests where available; they were not all forced in Chrome.
- No automated axe scan or full screen-reader pass was run. Browser automation in this session exposes read-only DOM evaluation, so scripts were not injected to bypass that limit. Duplicate IDs have a real rendered-component probe; touch sizes have DOM geometry evidence. Reduced motion, 200–400% zoom/reflow, A4 invoice print and every destructive confirmation need a dedicated follow-up verification pass.
- Dev-only Next issue badges, initial chart animation frames and the PWA install prompt appear in some authentic captures. They are not counted as Production layout defects. The install prompt was dismissed before later captures. Chrome logs showed dnd-kit described-by hydration mismatches in Notes/Settings and initial chart dimension warnings; reproduce those in a clean browser/production build before treating them as confirmed Production bugs. Use stable DndContext IDs if reproduced.

## Implementation order

1. **Protect work and correct counts:** C01–C06, explicit limits and owner-scoped aggregation. Tests first for the observed failures, no publishing behavior changes.
2. **Shared consistency:** U07/U08/U12/U16; establish title owner, control variants, focus restoration, width/spacing tokens. Validate existing destinations before rolling out.
3. **DNESKAi workflow:** U01/U02/U03/U09/U10; bounded topic inbox, stable review layout, source/mix/music access, recovery. Real saved pixels remain the approval surface.
4. **Destination cleanup:** U04/U05/U06/U11/U13/U14/U15; work card height, bounded settings, focused finance routes, filters and library cards.
5. **Measure and verify:** payload/thumbnail experiments, query plans, EN/CS, themes, 360/430/768/1024/1440/1728, keyboard/axe/screen reader, error states and A4 invoice regression. Publish no content as a side effect of a visual test.

Each batch should be a separate reviewable change with before/after evidence. Keep meaningful commits; do not split arbitrary lines or add empty commits to inflate contribution counts.
