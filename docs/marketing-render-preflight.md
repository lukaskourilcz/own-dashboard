# Marketing renderer diagnostic

The existing authenticated `POST /api/marketing/n8n` accepts this diagnostic operation. Since 2026-10-22 a `dneskai` brand
answers `410` `{"code":"route-retired"}` (audit finding cost-06); `devshark` works as before.

```json
{
  "operation": "render-preflight",
  "brand": "devshark",
  "sourceId": "EXISTING_PRODUCER_SOURCE_ID",
  "scheduledAt": "FUTURE_ISO_TIMESTAMP"
}
```

The server requires `VERCEL_ENV=preview`, the active fixed owner-bound pilot, marketing AI consent, an existing verified owned Instagram account, and the current trusted Claude Design template approval. The schedule must be in the next six days. The request cannot supply a source packet, template, account, owner or approval. A paused publishing account can still support this diagnostic.

The diagnostic covers devShark's single-layout renderer only. A `"brand": "dneskai"` request is refused with `render-preflight-source-kind-unsupported` before any template, account or source read; DNESKAi slides render through the vendored carousel studio (see below and `docs/marketing-generation.md`).

The server loads the owned source head and refreshes it from the producer. It uses only an eligible, unexpired question or coding task with a verified canonical content hash. It renders the exact authored question, options, answer, explanation and code, or the deterministic public coding challenge. An in-memory revision labels its caption “Renderer diagnostic only.” The server rechecks the producer, pilot and template before returning success. Article layout diagnostics are currently unsupported.

The response contains `diagnosticOnly:true`, `providerCalls:0`, `storage:"not-exercised"`, an asset count, JPEG/SVG SHA-256 hashes, dimensions and byte counts. It contains no source copy, caption, JPEG bytes, private URLs, account identifiers or credentials. The operation makes no model or trace call, job reservation, database write, storage upload, revision save, approval or publication. A successful response verifies rendering in that runtime; it does not verify Storage or grant publication readiness.

The renderer classifies missing brand/font/design files, native module imports, rasterization, JPEG encoding, geometry and layout failures using fixed codes. It discards exception messages, causes and filesystem paths. Template digests, fonts, layout, fact checks and approval requirements stay unchanged.

For future Instagram question/challenge jobs, the worker exercises this authored renderer after its authoritative source/template checks and before its first model invocation. The check uses memory only. It does not reset pilot reservations or permit a failed job to retry.

A DNESKAi deck job has no authored layout to exercise, so the worker checks only the native encoder. Before the source refresh, the daily generation reservation and the model call, `assertDneskaiJpegEncoderAvailable` (`services/marketing-worker/protocol.ts`) encodes one 1 × 1 JPEG in memory through the slide encoder's chain (`preflightDneskaiJpegEncoder` in `src/lib/marketing/dneskai-render.ts`). If sharp or libvips does not load or cannot encode, the job fails with `render-jpeg-encoder-unavailable` and costs nothing. `tests/lib/marketing-dneskai-worker.test.ts` replaces the sharp import with a load failure and checks that no reservation, model call or render follows.

Generation trace status `review` describes successful copy validation. The durable job and saved ready revision determine whether the complete preparation succeeded. If later preparation fails, the worker attempts an exact-revision-bound root trace update with a fixed failure code while preserving the measured copy usage and hashes. This diagnostic update is best effort: indexing delay or a tracing outage can prevent it, and the worker performs no diagnostic network retry. The durable job remains the authority for failure.

Local tests exercise real JPEG rendering from retained authored fixtures under explicitly labelled eligibility/approval simulations, missing files/native modules, API authentication and field rejection, producer withdrawal, pre-paid holds and trace privacy. Retained fixtures and public template manifests remain unapproved/ineligible. These tests do not prove a deployed Linux renderer, Storage upload or a live provider result.

## Native JPEG packaging

The first deployed zero-model diagnostic returned `render-jpeg-encoder-unavailable`. The local Next.js 16.2 output trace included Sharp's native addon but omitted its installed libvips dynamic library. An isolated package containing only the traced public dependencies failed to load Sharp; adding that one library made the same package load. Both Sharp 0.35.5 official ESM and CommonJS exports are callable locally. This demonstrates a local packaging defect; the deployed failure still needs verification after the fix.

The fix first added `./node_modules/@img/sharp-libvips-*/lib/**/*` to the two devShark render routes and the offline import only. The integration build of 21 October showed that every other marketing route whose trace contains the sharp addon still shipped without the library: `/api/marketing/tick` (scheduled DNESKAi generation and media collection, the only place source pictures are inspected), `/api/marketing/revisions` (owner edits re-render the deck), and `/api/marketing/dneskai/media` (the owner's read-only media tray), `/dneskai/collect`, `/dneskai/review`, `/dneskai/costs`, `/jobs`, `/jobs/[id]` and `/diagnostics/[id]`, whose module graphs pull in sharp. The include now sits on the `/api/marketing/**` rule, so every marketing function, including one added later, carries it. The pattern includes installed runtime libraries across platforms without selecting an architecture or installing a new dependency. Next.js already externalizes Sharp, so the fix keeps its loader, dependency version and template digests unchanged. The regression test builds an isolated public package without the library, confirms failure, adds the configured library directory and encodes a real JPEG through the official ESM export. It passes no inherited credentials or instrumentation hooks to the child process. A second test walks the runtime imports of every App Router route handler and fails when a handler that can reach sharp gets no libvips include under Next's own key matching, or when `/api/marketing/**` loses it.

The local Next.js output-tracing guide permits narrow route-scoped runtime asset includes. Sharp documents deployment binary requirements and externalization in its [installation guidance](https://sharp.pixelplumbing.com/install/). The existing Preview diagnostic must verify the rebuilt deployed renderer with zero provider calls before any additional generation authorization.

## DNESKAi studio renderer packaging (#117)

The DNESKAi renderer (`src/lib/marketing/dneskai-render.ts`) runs `@boardlessai/carousel-studio`, vendored in `vendor/carousel-studio/`. The studio finds its fonts and the DNESKAi brand kit through paths derived from its own module URL and hands every committed face to resvg with system fonts switched off. A function that lacks those files draws no text, which is how Quorum's own render route answered 500 in production.

- Its `node_modules` entry is a link into `vendor/`, so Turbopack bundles the studio as project code and rewrites `import.meta.url` to the project-relative `vendor/carousel-studio/dist/...` path, resolved against the function root at run time. `serverExternalPackages` cannot externalize a linked package; it lists `sharp` and `@resvg/resvg-js`, whose native bindings must stay external.
- `outputFileTracingIncludes` adds `./vendor/carousel-studio/fonts/**/*` and `./vendor/carousel-studio/brand-kits/**/*` to every `/api/marketing/**` function, so a future route that renders (the review UI, the scheduled tick) cannot ship without them. The same rule carries the libvips include described above.
- The renderer imports `@boardlessai/carousel-studio/dneskai-slide` and `@boardlessai/carousel-studio/fonts`, two subpath exports of the vendored manifest, and never the package barrel. The barrel also carries the studio's hook-library reader, whose file reads take a path Turbopack cannot scope; bundling it traced the whole repository (docs, tests, migrations, 1,439 files) into each marketing function. With the subpath the execute route traces 583 files. `dist/fonts.js` is already part of the slide API's module graph, so the second subpath adds no file to a trace.
- Tailwind's automatic source detection skips `vendor/` (`@source not "../../vendor"` in `src/app/globals.css`); the built studio adds no classes, and the compiled CSS is identical with and without it.

`npm run build` on 20 October 2026 (Next.js 16.2.6, Turbopack) passed with no warnings. The traces of `/api/marketing/jobs/[id]/execute` and `/api/marketing/n8n` each list all 46 committed faces with their OFL files and the ten caught-up kit files, and copying exactly the traced files into an empty directory left every face and the kit at the path the bundled studio reads. That verifies the local build output, not a deployed function: render one deck in Preview after the integration deploy (#123) before relying on it.

`tests/lib/carousel-studio-vendor.test.ts` guards the pieces that do not need a build: the tree hash, one shared sharp, resvg and zod, the subpath exports, the face and placed fields of every DNESKAi template, the include globs and the eleven golden PNG hashes. `tests/lib/marketing-dneskai-render.test.ts` renders one slide of every type from generated photographs and checks the JPEG constraints, deterministic bytes, cache hits, and refusal on clipped text, a character the face lacks, text the slide type does not draw, low-resolution bleed and missing media. `npm run check:render-traces` (`scripts/check-render-traces.mjs`) inspects the `next build` output, and CI runs it right after the Build step of the `check` job. It reads the `.nft.json` traces of `/api/marketing/tick`, `/revisions`, `/jobs/[id]/execute`, `/dneskai/media`, `/n8n` and `/offline-import`, and fails unless each one lists a `libvips-cpp.so` from the root `node_modules/@img/sharp-libvips-<platform>/lib` for the addon's platform, at least one font under `vendor/carousel-studio/fonts/` and sharp's native addon, each present on disk. Copies inside other packages, such as the sharp that `next` carries, do not count. It prints one line per route, and the `.so` name ties it to a Linux build. On 21 October 2026 it passed on the local build (every route: libvips 8.18.7, sharp-linux-x64 0.35.5, 46 fonts) and failed for `/api/marketing/tick` while that trace's libvips entries were removed.

The check does not look at the brand kit or at files outside the project root. The #117 build was checked for both by hand: the trace of `/api/marketing/jobs/[id]/execute` lists all 46 faces, the 10 caught-up kit files and one sharp 0.35.5, and nothing outside the project root.
