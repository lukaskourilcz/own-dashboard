# Marketing generation and rendering

This server-only marketing workflow accepts public authored source packets after the owner enables marketing-source consent. It sends their content to Claude. It never sends OwnDashboard project notes, contacts, invoices, financial records, learner responses, hidden grading tests or server solutions. The existing non-marketing no-model-call boundary still applies. No model or LangSmith network call ran during implementation.

## Bounded generation

`src/lib/marketing/generation.ts` exports `generateMarketingDraft(input, dependencies)`. Input includes a strict `SourcePacket`, account, schedule, template version, revision UUID, up to eight brand-matching presentation references and `consent: true`. Dependencies supply a configured `MarketingModel`, optional tracer/abort signal/clock, and a validated budget. The worker verifies source eligibility, expiry, brand/locale, content hash and a future schedule before provider admission. An Instagram reference can inform presentation; it cannot replace an article or exercise source.

`createClaudeMarketingModel({apiKey, model, pricing})` uses server TypeScript LangChain `ChatAnthropic` with SDK retries disabled. The call shape follows the model (`claudeCallProfile` in `claude-call-profile.ts`, which the Saved-source analysis in `knowledge-extraction.ts` uses as well, because both read `MARKETING_CLAUDE_MODEL`). Claude Sonnet 5.5 rejects forced tool use, non-default sampling and disabled thinking, so it answers through structured outputs (`output_config.format`, LangChain `method: "jsonSchema"`) with `thinking: {type: "between_tools"}` (no extended thinking, so the whole output budget goes to the answer) and `effort: "low"`. Claude Opus 4.7, Opus 4.8, Opus 5, Opus 5.5, Sonnet 5, Haiku 5.5, Fable 5 and Fable 5.1 reject a sampling override (Opus 5.5 and Fable 5.1 also forced tool use), so they answer through structured outputs at `effort: "low"` with the model's own thinking default; none of these shapes has been sent to the real API yet. Older models keep the forced strict tool call at temperature zero. Server-side refusal fallback is not enabled: a fallback model would write text that the revision's `model` field does not name.

The model is `MARKETING_CLAUDE_MODEL`, or `claude-sonnet-5-5` when it is unset (owner decision 5, #110). The rates are `MARKETING_CLAUDE_INPUT_USD_PER_MTOK` and `MARKETING_CLAUDE_OUTPUT_USD_PER_MTOK`; when one is unset and the model is the default, Sonnet 5.5's standard $2 input / $10 output per million tokens apply (platform.claude.com pricing, 20 October 2026). Another model with an unset rate refuses with `claude-pricing-required`, so it never borrows Sonnet's prices. The rates are a setup reference, not a live billing feed. `ANTHROPIC_API_KEY` and `MARKETING_AI_CONSENT=true` stay mandatory.

The default budget allows two attempts, at most 20,000 reserved input tokens and 2,500 output tokens per attempt, $0.13 total estimated cost and 60 seconds for generation. A 60-second HTTP host should choose a shorter generation limit to leave time for rendering, uploads, source refresh and diagnostics. The reservation uses UTF-8 prompt/schema bytes plus envelope headroom. It is conservative admission arithmetic; billing reconciliation uses actual provider usage.

**Why $0.13 (owner decision 15, 22 October 2026).** The cap was $0.25. Two full attempts at Sonnet 5.5 prices cost 2 × (20,000 × $2 + 2,500 × $10) / 1,000,000 = 2 × $0.065 = $0.13, so $0.25 reserved about twice what a job can spend; a typical post costs about $0.024. The cap is enforced, not just computed: an attempt is made only when the recorded spend plus that attempt's reservation (its input counted in UTF-8 bytes, which are never fewer than the billed tokens, plus the full 2,500 output tokens) stays within $0.13. A brief with rich Czech evidence can reserve more than $0.065 for one attempt; if its first attempt was expensive too, the retry is refused with `cost-budget-exceeded` instead of passing $0.13. Ledger rows written at $0.25 before the change keep their $0.25. No prompt caching, browsing, model tools, fallback provider or LLM judge participates.

Only known usage with invalid copy permits another attempt within the remaining reservation. Unknown usage, transport errors and provider failures stop without a retry because billing may already have happened. The durable runner must record provider admission before calling the model and reconcile a crash after admission rather than replay it.

Zod rejects schema drift and additional fields. Deterministic QA checks locale, unsupported URLs/HTML/control characters/emoji, novel numeric strings, evidence indices and missing article citations. Those checks do not prove semantic entailment or language quality. The owner reviews factual claims, natural Czech/English and evidence before approving the exact final revision hash.

For devShark the renderer receives original authored question text, option order, answer, explanation and exact source code. It never reconstructs these from model output. It removes recognized Markdown emphasis markers from displayed authored prose and moves a matching fenced code block into the exact-code slide; a mismatch holds the job. A coding task without a safe authored explanation becomes a challenge-only carousel: complete measured public spec, exact starter code and fixed CTA/caption. Model-written solutions and claims are discarded; overflow holds before a provider call. The model supplies title/caption for review; generated code is forbidden. DNESKAi copy remains Czech and links the exact article/evidence revision. devShark remains English. A final caption includes the canonical source URL; Threads captions exceeding 500 characters hold the draft.

## Humanizer in the structured generation call

The owner-requested [Humanizer skill](https://github.com/blader/humanizer/tree/225a6f39ac85f76ee48dbad772ea4abe4ed6c9d8) is pinned at commit `225a6f39ac85f76ee48dbad772ea4abe4ed6c9d8`, version `3.1.0`, MIT. `templates/marketing/humanizer/SKILL.md` and `LICENSE` preserve upstream bytes verbatim; `provenance.json` records their hashes, size, license, adaptation scope and source sections. This is a repository-local integration, with no global plugin installation.

`src/lib/marketing/humanizer.ts` derives `marketing-humanizer/2` from the upstream embedded editing mode. It supplies at most 2,500 UTF-8 bytes of instructions per call, rather than transmitting the full 32,348-byte skill. The adapter fingerprints its version, exact upstream commit/skill hash, review instructions and both language voices with `MARKETING_HUMANIZER_POLICY_FINGERPRINT`. Every actual generation system prompt includes that fingerprint and provenance. `marketing-copy/3` marks the changed generation prompt; older revisions and approvals retain their stored versions. Version 2 (22 October 2026) adds one sentence to the Czech voice: when the rules ask for a cover hook, a cover headline and first caption sentence that state the story's most concrete true fact are not a canned hook. The ban on canned and withheld-subject openings stays. The English voice and the review lines are unchanged, but the policy fingerprint covers both voices, so devShark prompts carry the new fingerprint too.

Within the existing Claude structured-output call, the model drafts, reviews and rewrites generated prose before returning only the final schema. The instructions ask for natural Czech reporting for DNESKAi and plain English for devShark. They remove staged hooks, hype, forced triads, repeated summaries, decorative labels and habitual dashes while preserving selected supported facts, scope, uncertainty, attribution and evidence indexes. They prohibit invented first-person experience, reactions, quotes and expert authority. This factual workflow narrows upstream voice matching and creative reactions: reference text cannot override the source or safety rules.

Only generated titles/captions and generated article slide prose receive style review. The server still supplies authored exercise text/options/answer/explanation/code and the full challenge specification; Humanizer cannot rewrite them or invent a solution. Challenge-only title, caption and CTA remain deterministic. The model response then passes the existing strict-schema/source/cost/QA gates, followed by rendering, source revalidation, hashing and separate owner approval. No second rewriting call, model judge, provider/key change, new tools or larger budget is added. Adapter bytes count toward the existing conservative input reservation, so a source exceeding that unchanged cap remains held.

Focused offline tests verify verbatim provenance, bounded instructions in the actual invocation for both brands, one-call valid drafts, unchanged usage/cost arithmetic, immutable authored exercises/challenges, existing fabricated-number/schema refusals, and consent/source/admission holds before invocation. Those tests make zero provider calls. Style instructions do not prove human quality or general factual entailment; the owner still reviews the exact final prose and evidence before approving its hash.

## DNESKAi briefs: generation v7

`marketing-copy/7` (`src/lib/marketing/dneskai-generation.ts`, run by `generateMarketingDraft` for a `SourcePacket` of kind `brief`) turns one research brief (`dneskai-brief/1`, #115) into a rendered Instagram revision with one structured call. The model writes the caption, the title, the slides and their alt texts, and picks pictures from the brief's media by sha256. Code writes the rest: the caption's AI disclosure and hashtags. The owner's post rules (22 October 2026, `.claude/skills/dneskai-post-content/SKILL.md`) hold throughout: the first slide shows only its headline; no slide shows a page count, a picture credit or a sources slide; neither slides nor caption say anything about sources or verification; a caption carries at most 10 hashtags.

**What the model sees.** The system prompt (`DNESKAI_BRIEF_SYSTEM_PROMPT`) holds the rules and the Humanizer's Czech embedded review. The human turn is JSON: the brief's title, category and date; the evidence with publisher, title, a bounded excerpt, the Prague publication date unless it is estimated, and `captionOnly`; the media with sha256, evidence index, original position, credit, origin, size and three capability flags (`fullBleedCapable`, `insetCapable`, `singlePhotoCapable`; see below); the rules code derives from the media; and `presentationOnly: []`. No picture bytes reach the model, and no URL except an education brief's evidence links (below). The prompt fits the input budget: excerpts shorten, then sources and pictures drop, until it does; the primary source always stays. `MARKETING_BRIEF_PROMPT_FINGERPRINT` hashes the version, system prompt, both wire schemas and text limits; a revision's `promptVersion` is `marketing-copy/7+<first 12 hex>`, and a test pins the value.

**Rules.** Facts come only from the evidence text, and every number in the title, caption, headlines, bodies, kickers and alt texts must appear there (a Czech decimal comma matches an English point). A number the evidence states only inside a date is not a fact (owner decision 18): „22. 10. 2026“ supports „22. října“ and „v roce 2026“, never „22 %“ or „2026 firem“. `dneskaiUnsupportedNumbers` splits the dates out of the copy and the evidence first: Czech „22. 10. 2026“, „22.10.2026“, „22. října 2026“, „v říjnu 2026“, „v roce 2026“, English „October 22, 2026“, „22 Oct 2026“, ISO „2026-10-22“ and „10/22/2026“. A number in a date of the copy may match any number of the evidence; any other number must match a number outside the evidence's dates. A numeric date needs spaces or a year, so a version such as „Opus 5.5.“ stays a number. Evidence with `captionOnly` is text an author posted under an Instagram post or Reel, never speech from a video. The register is DNESKAi's: calm, direct, skeptical, without hype, emoji, URLs or hashtags in the prose. A claim is attributed to its actor inside the sentence („Anthropic uvádí, že…“); no sentence talks about sources, confirmation or verification. `dneskaiTalksAboutSources` refuses such sentences in slides, alt texts and the caption (`source-talk`), for example „Zdrojem je oznámení samotného…“, „Údaj pochází od…“, „nezávislé potvrzení chybí“ or „Z dostupného textu nevyplývá…“.

**Cover hook (owner decision 1, option B of the [carousel playbook](reports/dneskai-audit-2026-10/research/carousel-playbook.md#8-register-options-for-the-owner), 22 October 2026).** The headline of the first slide, or of the single slide of a single-image post, states the most concrete and surprising true fact of the story as a plain declarative sentence: a number, a date, a named actor or a precise change, as strong as the evidence states it. The next slide or the caption backs it up. The caption's first sentence, at most 125 characters (where the feed folds), states the same fact in fuller form. No question, exclamation, teaser that withholds the subject, superlative, or „first“/„breaking“ the evidence does not state. Every other slide stays calm. The truth rules and gates are unchanged. The playbook's `hook` family tag, its 20 % cap and the fixed series kicker are not built. The model cannot see the pictures, so it never describes one; alt text names the slide's message and whose picture it carries.

**Answer shape** (`DneskaiCopySchema`): `title` (≤ 160), `caption` (≤ 1,500, aimed at 300-700), `hashtags` (≤ 10; the prompt asks for up to 9, most specific first), `format` (`carousel` or `single-image`) and 1-7 `slides`, each `{ type, variant?, headline, body?, kicker?, images: [{ slot, assetSha256, crop? }], alt }` with type `cover-photo`, `figure`, `split`, `statement` or `single`. There is no credit or sources field, and no slide carries either. A cover or single slide takes only `headline`.

**Gates before render** (`validateDneskaiCopy`), each a named issue with slide and field:

- the format the brief allows (`suggestedFormat: single-image` allows only that; the brief suggests it only for a thin evidence pack, never because of the picture count, and a carousel brief without pictures gets `firstSlide: statement` and `minimumPictureSlides: 0`); a single-image post is exactly one `single` slide; a carousel has no `single` slide;
- pictures only from the offered media, each used once; `cover-photo` only with `fullBleedCapable`, `single` (variant `photo`) only with `singlePhotoCapable`, `figure` and `split` only with `insetCapable`; the image count and slots each type takes;
- the first carousel slide is `cover-photo` when a full-bleed picture is offered, otherwise `figure` or `statement` (only `statement` without framed pictures); a single slide is `photo` exactly when a `singlePhotoCapable` picture is offered; with two or more usable pictures at least two slides show one;
- only the fields the slide type places (`DNESKAI_PLACED_FIELDS`), each under its template's character ceiling (`DNESKAI_TEXT_LIMITS`, read back from the vendored templates by a test);
- alt text that is not the headline; no URL, markup, control character, emoji or caption hashtag; no number the evidence does not state; no sentence about sources or verification (`source-talk`);
- a caption that fits 2,200 characters once code appends the AI disclosure and the hashtags.

Then code builds the deck (`buildDneskaiDeck`) and runs `validateDneskaiDeck` on it with the stored source media. A blocking problem on a written slide (`text-clipped`, `unsupported-glyph`, `image-low-resolution`, `text-unplaced` and the rest) fails the attempt.

**The one retry.** A failed attempt with known usage gets one retry inside the budget (two attempts, $0.13, 20,000 reserved input and 2,500 output tokens per attempt). The retry turn lists every issue as an instruction that names the slide by place, type and picture hash prefix, the field and what to do (for a clipped field: rewrite it to at most three quarters of its length). The model's previous answer is added when it still fits the input budget. Unknown usage and provider failures never retry. Retry instructions repeat no free text of the model's.

**The retry runs on the next tick (GEN-14).** Both attempts, the studio gate and the media reads used to share one 45-second generation limit, so a slow first answer left the retry too little time; an abort mid-call books the job's whole maximum (then $0.25, now $0.13). The scheduler now calls `executeMarketingJob` with `deferRetry: true`. When the first attempt fails copy validation with known usage, `generateMarketingDraft` throws `MarketingGenerationRetryDeferred` instead of retrying. The worker then puts the job back to `queued` with a fenced conditional update (`status = 'running'`, same fence, live lease; no new SQL function). The update stores `{ schemaVersion: "marketing-job-retry/1", resume: { attempt: 1, feedback, issues, usage } }` in `marketing_jobs.result`. The feedback is the same targeted retry text, including the model's previous answer when it fit; it sits on the owner's own job row, which only the owner and the service role can read. The next tick claims the same job, reads that state under its new fence and makes attempt 2 with a fresh 45 s. The cap is still two attempts, and the $0.13 per job counts from the stored usage. The reservation and the daily ceiling are unchanged: attempt 2 reserves the job's whole maximum again under the new fence, and between the ticks the ledger counts the queued job at its reservation. A provider failure, a timeout or unknown usage still fails the job without a retry. Stored state that does not parse, or that would allow a third attempt, fails the job before any call (`job-retry-state-invalid`, `generation-retry-invalid`). If the requeue write is lost, the lease expires into reconciliation, as with a lost finish. A failure before attempt 2 still records attempt 1's usage. The first call's trace finishes `failed` with `generation-retry-deferred`; the second call has its own trace. The pilot path and the worker-role execute route keep the in-process retry, but they also honour a stored retry state.

**The revision.** `marketing-content/2` with the deck, format `carousel` or `post`, brand `dneskai`, the request's Instagram account and schedule, `templateVersion` `DNESKAI_DECK_TEMPLATE_VERSION` (the vendored renderer, `carousel-studio/<version>+<commit>`), no knowledge ids and no assets. The draft's legacy `slides` list is empty, as after an owner edit. A request's optional `engagement` (#157, the owner's keyword and messages) is copied onto the revision unchanged; the prompt never contains it. The worker renders the deck through `renderDneskaiRevisionAssets`, checks readiness and stores `content_hash = revisionContentHash(revision)`.

Code-written parts:

- the deck is the written slides only, with no credit and no sources slide (`buildDneskaiDeck`). The pictures' credits and origins stay in `marketing_media_asset_links` and the brief, never in the post;
- the caption is the model's text, then the AI disclosure (`DNESKAI_AI_DISCLOSURE`, „Text připravil jazykový model. Výběr a schválení: redakce DNESKAi.“; it describes how the post was made and claims no legal requirement), then at most 10 hashtags (`dneskaiHashtags`): Latin letters and digits as the studio's `normalizeHashtag` gives them, `#dneskai` first, then the model's tags in its order, then `ai umelainteligence technologie aitech` only while room is left. No source list, link or credit. A caption the owner edits is refused above 10 hashtags (`caption-hashtags-over-limit`).

**The DNESKAi job.** `DneskaiDeckJobRequestSchema` (`services/marketing-worker/protocol.ts`): a brief packet, no template, no knowledge, Instagram only, `templateVersion` equal to `DNESKAI_DECK_TEMPLATE_VERSION`. `dneskaiBriefJobRequest({ source, account, revisionId })` builds one from a brief packet; `enqueueMarketingJob` admits it with the usual consent, source, schedule and account checks. A queued job whose template version no longer matches the vendored studio fails with `template-superseded`. Generation refuses before any call without the media loader (`dneskai-media-loader-required`), with knowledge, for Threads or for another template version.

## Education posts: the DM and the keyword line (#158)

A generation request may carry `education: { keyword }` (an education topic and its suggested keyword). Then the call uses `DneskaiEducationCopySchema`, the news schema plus `replyMessage`, and the human turn gains `education: { links, rule }`: up to six evidence URLs, the only URLs the model ever sees, and `DNESKAI_REPLY_MESSAGE_RULE`. The system prompt is the same as for news, so a news call is unchanged apart from its version. `validateDneskaiReplyMessage` holds the DM to the caption's truth rules: 400 to 900 characters, at most one URL and only an evidence link, every number from the evidence (step markers „1.“ to „9.“ at a line start excepted), no markup, emoji, hashtags, text about sources or call to comment. A failure retries like any other copy issue. The draft carries `engagement: { keyword, replyMessage, publicReply: "Poslali jsme vám to do zpráv." }`.

`assembleDneskaiCaption` adds the code-written line „Napište do komentáře „KEYWORD“ a pošleme vám návod do zpráv.“ (`dneskaiKeywordLine`, `src/lib/marketing/dneskai-caption.ts`) before the AI disclosure whenever the draft has a keyword. The model rules still forbid any call to comment. The line holds no hashtag, so the ten-hashtag cap (`DNESKAI_HASHTAG_LIMIT`, `DNESKAI_CAPTION_HASHTAG_MAX`) is unchanged. A regeneration that carries the owner's `engagement` keeps it, asks for no new DM and writes the line for the owner's keyword. A news request sends neither field and gets neither. Every owner edit runs `dneskaiCaptionWithKeyword`, so the line follows a changed keyword and goes with a removed one; the Lab does the same in the draft. The brief path sets `education` (#222): when a topic brief (`marketing_dneskai_briefs.topic_id`) is queued and its topic is `education` with a keyword, `dneskaiTopicEducation` puts `education: { keyword }` in capitals on the job. A news topic, a night brief and a missing or invalid keyword get nothing, so those posts carry no DM draft or keyword line unless the owner adds a keyword in the Lab's editor (#159). Topic briefs exist only with `DNESKAI_TOPIC_BRIEFS_ENABLED`.

## DNESKAi daily generation ceiling

Before every paid DNESKAi model call, the retry included, the worker calls `marketing_reserve_dneskai_generation(owner, job, fence, reservation, ceiling)` (migration `20261021124651`). Under an owner lock it sums the DNESKAi generation spend of the last 24 hours in `marketing_private.dneskai_generation_spend` and refuses with `dneskai-daily-generation-budget-exhausted` when that sum plus this job's whole maximum ($0.13 by default; $0.25 before 22 October 2026) would pass `MARKETING_DNESKAI_DAILY_GENERATION_USD` (default 1.00). A finished job counts at the cost it recorded in `marketing_jobs.result.usage.estimatedCostUsd`; a running job, a job in reconciliation and a failed job without a recorded cost count at their full reservation. When a call ends without a usage figure (a transport or provider failure, or a response without usage), the brief job records its whole maximum as its cost, so unknown usage always counts as the full reservation. One exception (owner decision 16): a call that provably billed nothing records no cost. That is a call our code refused before sending (`unsafe-native-tracing-enabled`, `provider-sdk-setup-failed` raised before the request), or an HTTP answer the Messages API returns instead of running the model: 400 (including LangChain's `CONTEXT_OVERFLOW`, raised only for a 400), 401, 402, 403, 404, 413, 429 and 529 (`marketingProviderFailureUnbilled` in `provider-errors.ts`). The calls are non-streaming with SDK retries off, so the status is the whole answer. Every other failure keeps the full reservation: no HTTP status (dropped connection, timeout, abort, an error event inside a response), 408, 409, 500, 502, 503, 504 or any other status. A refusal the model returns as an answer (`stop_reason: refusal`) carries usage and is counted at that usage, which is $0 when the usage is zero. None of these failures retries. `generateMarketingDraft` refuses a brief without the admission hook (`dneskai-daily-generation-budget-unavailable`) before any call; `executeMarketingJob` always wires it. A ceiling below one job's maximum refuses every DNESKAi call, so the effective minimum is $0.13. A failed job records its usage as `{ schemaVersion: "marketing-job-failure/1", usage }`, which `readMarketingJob` does not return as a result. A ledger outage or an unreadable answer refuses the call (`dneskai-daily-generation-budget-unavailable`); a malformed ceiling refuses every DNESKAi call (`dneskai-daily-generation-budget-invalid`). devShark jobs do not touch the ledger. The October staging pilot reservations are separate and unchanged.

## DNESKAi slides: the vendored carousel studio

Since #117, DNESKAi has no layout of its own in this repository. Every DNESKAi slide renders through `renderDneskaiSlide` in `@boardlessai/carousel-studio`, the Design Lab engine from Quorum (quorum#603), vendored as built output in `vendor/carousel-studio/` and installed as `"@boardlessai/carousel-studio": "file:vendor/carousel-studio"`. The single-layout template `dneskai-editorial/2` (Claude Design, never approved), its derived layout and its brand and logo copies are deleted, and the staging approval receipt accepts devShark entries only. A DNESKAi entry in `MARKETING_PILOT_TEMPLATE_APPROVALS` now fails the whole receipt closed.

`src/lib/marketing/dneskai-render.ts` implements the `RenderDneskaiDeck` port from `dneskai-ports.ts` through `createDneskaiDeckRenderer({ storage })`:

- Each `DneskaiSlide` (`dneskai-slides.ts`) maps to the studio input: type, variant, words, `sources`, the photographs loaded with `loadMedia(assetSha256)` together with their crop, the slide's place in the deck (`{ index, count }`) and locale `cs`. The studio writes the folio, the sources title and the disclosure. A photograph used on several slides is loaded once per deck.
- The gate is the studio's plus three rules, so that the copy the owner approves is the copy that prints, whole and legible:
  - `text-clipped`, which the studio only reports, refuses here: cut Czech copy never ships. A slot the renderer cut without the studio reporting it refuses the same way.
  - `unsupported-glyph`: every drawn field is checked, as the studio draws it (trimmed, NFC, the kicker uppercased in Czech), against the committed face it is set in: headline in Space Grotesk 700, body and source lines in Source Serif 4 400, kicker and credit in IBM Plex Mono 400. The studio's DNESKAi API draws a character its faces lack as an empty box, or in another face, and reports nothing; an emoji, CJK or ✓ refuses the deck and the message names each character with its code point. The check reads the studio's own metric tables through the `./fonts` subpath (`resolveFace`, `missingCommittedGlyphs`), which are also what its fitter measures by. They cover Latin-1, Latin Extended-A and the common punctuation, including „ “ – — … × § %, but not U+201A ‚ (the Czech nested opening quote), ≥ ≤ ← ↗ ✓ • ™ π Ω.
  - `text-unplaced`: written text the slide type does not draw. The studio fills only its template's slots, so this text would sit in the approved deck and never reach the picture. Cover photo draws headline, kicker and credit; figure headline, body and credit; split and single headline, body, kicker and credit; statement headline and body; sources only its source lines. Blank text is no text.

  `tests/lib/carousel-studio-vendor.test.ts` derives the face and the placed fields of every vendored DNESKAi template from the studio itself and fails when `DNESKAI_FIELD_FACES` or `DNESKAI_PLACED_FIELDS` disagree, so a re-vendor cannot move a field unnoticed. Missing or undecodable photographs, a full-bleed photograph whose shorter side is under 900 px or whose crop stretches it more than 1.5×, a bad crop and a loader failure (`media-asset-unavailable`) refuse as well; a loader failure after the job's deadline is `worker-timeout` instead. One blocking problem on any slide refuses the whole deck, returns every problem with its slide, code, field and message, and stores nothing. When the text gate refuses, the remaining slides are validated, not drawn. `image-upscaled` renders and is reported.
- Each slide becomes a baseline JPEG: exactly 1080 × 1350, quality 92, 4:4:4 chroma, sRGB with an embedded sRGB profile, at most 8 MiB. The encoder output is read back and checked before upload.
- Assets come back in slide order in `AssetSchema` shape with the slide's alt text, together with each slide's render key.

`validateDneskaiDeck(deck, loadMedia, signal?)` returns the same problems, the text gate included, without rendering or storing anything; generation v5 uses it to fit copy before the deck is rendered.

### Render cache

A slide's render key is `sha256(canonicalJson(…))` over the vendored engine (version, Quorum commit and tree hash), OwnDashboard's render policy (`dneskai-render/2` since the glyph and placement gates; every `/1` object is re-keyed and rendered once more), the encoder (sharp and libvips versions plus the JPEG settings), the words as the studio takes them (trimmed, blank source lines dropped), the variant, every photograph's asset hash and crop, and the slide's position. The studio's template choice and payload are pure functions of exactly these inputs, so the key hashes the inputs and a cache hit loads and decodes no photograph. The alt text is not drawn and is not part of the key. The key deliberately differs from the issue's `templateSha, payload, assetSha256[], focal[]`: under a pinned vendored tree the two are equivalent, and keying the inputs lets a hit skip the photographs.

`createDneskaiSlideStorage(db, owner)` in `worker-runtime.ts` keeps one immutable object per owner and key at `<owner>/marketing/dneskai/slides/<renderKey>.jpg` in the private `marketing-assets` bucket. It shares the devShark upload path: private-bucket check, `upsert: false`, size, type and metadata check, re-download with a sha256 comparison, then a seven-day signed URL. `find` verifies the stored bytes against the recorded sha256 before it signs; a tampered or foreign object fails instead of being replaced. Metadata records the owner, render key, JPEG sha256, renderer version and policy, studio template id and version, PNG and SVG hashes and any non-blocking problems, so a cache hit reports what the original render reported. Nothing revision-specific goes into an object, which is what lets every revision that draws the same slide reuse it. An unchanged deck therefore loads, renders and uploads nothing; editing one slide re-renders that slide only; an engine, policy or encoder change re-renders each slide once.

### Worker routing

`runMarketingWorkerJob` sends a DNESKAi Instagram draft to the deck renderer only when the draft carries a deck (generation v5, #116, attaches it). ## Deterministic JPEG rendering and storage (devShark)

`renderMarketingPreview(input)` allows local review of pending templates and rejects production environments. `renderMarketingAssets(input, storage)` requires a trusted Design-approved template. Instagram emits 1080 × 1350 JPEG slides, quality 92 with 4:4:4 chroma sampling, at most five slides and 8 MiB per JPEG. The renderer uses explicit pinned font files with system fonts disabled and validates original asset/font checksums.

Text fitting uses measured glyph advances, normalizes displayed prose to NFC, supports Czech diacritics, and fails on missing glyphs, long unbreakable words or vertical overflow. It preserves source-code identifiers, indentation and line breaks; code never wraps, truncates or normalizes Unicode identifiers. Unsupported code glyphs hold the render. A conservative collision gate also holds text that would overlap a surfacing fin. An overflowing exercise holds the job for an edited source/layout. It never creates a guessed replacement or fake product screen.

`MarketingAssetStorage.put({key, bytes, sha256, contentType, metadata})` returns `{url, sha256}`. The adapter must enforce owner-scoped storage, immutable object keys, no overwrite, and HTTPS access to exact JPEG bytes. The renderer rejects a returned hash differing from its local bytes. Metadata records revision UUID, template/export hashes, SVG hash and renderer version. Private storage with signed URLs is supported only when those URLs remain usable through the schedule and publication retries. Renewing a signed URL after re-verifying the bytes keeps the revision and its approval, because the approval hash excludes delivery URLs; see [DNESKAi revisions with media and crop](marketing-revision-media.md). Clean partial uploads after failed jobs with a retention policy.

Threads jobs skip rendering and retain a caption of at most 500 characters with an empty asset list. Store the final `ContentRevision` with its assets alongside the slide JSON. Hash the full final revision, including assets/account/schedule, before review. Source retirement, source supersession, changed assets, changed schedule or changed template requires a new revision and approval.

## LangSmith EU diagnostics

`createMarketingTracer` uses the explicit LangSmith SDK with `https://eu.api.smith.langchain.com` and EU web links. Configure an EU workspace/key; a hostname alone does not migrate a US workspace. Global LangChain/LangSmith tracing and verbose console tracing must remain disabled. The model call also runs inside a disabled traceable context. Native n8n workflow tracing does not represent this worker. LangSmith is diagnostics and evaluation. The approval record is `marketing_revisions.approved_hash` and nothing else.

The adapter hides inputs/outputs, filters metadata through strict schemas, disables runtime/environment metadata, prompt cache and debug logs, and uses one-second request timeouts with no retry; each diagnostic step also gives up after three seconds (`LANGSMITH_DIAGNOSTIC_DEADLINE_MS`). It records source ID/revision hashes, exact source content hash, stored revision UUID, model, hashed prompt/template versions, knowledge UUIDs, attempts, latency, token usage, estimated cost and bounded QA codes. Raw source/copy, URLs, credentials, owner notes and exception text do not enter traces. Resolve the source ID/revision hashes against OwnDashboard's stored source records.

A DNESKAi brief generation adds to its root run `event_id_hash` and `member_hash_hash` (sha256 of the brief's event id and member hash; `printf %s "$eventId" | sha256sum` finds the trace of a known brief) and `media_count` (the source pictures the brief offered). When it finishes, the root also carries `format`, `slide_types` (slides per type), `deck_media_count` (distinct pictures used), `attempts`, `estimated_cost_usd` and `retry_reasons` (the issue codes of the generation attempts that a later attempt followed; the last attempt's codes are never among them, so a run that failed on its only attempt has none, and its codes stay in `issue_codes`). Each attempt is a child run with its tokens, cost and issue codes. Captions, slide text, credits, evidence text and URLs never enter a trace. `tests/lib/marketing-tracing-brief.test.ts` walks every payload and fails on any field outside the allowlist and on any string that is not a hash, a UUID or a short code; a value passed as an issue code that is not a code is dropped.

`recordPreparedRevision` adds render latency, asset hashes and the final revision hash to the same trace after source revalidation. The adapter returns private EU trace links and never enables public sharing. A missing trace means diagnostics are unavailable.

A tracing outage stops nothing. In `generation.ts` a tracer that rejects, throws or hangs counts as no trace. The worker records the rendered revision on the trace as best effort (`services/marketing-worker/protocol.ts`), from the root metadata this tracer just wrote, so it does not wait for LangSmith to index the run. Owner feedback is sent only after the owner's action has succeeded, and its result is ignored. `tests/lib/marketing-tracing-outage.test.ts` covers refused writes while rendering and during approve, return, skip and edit.

`generation-benchmark.ts` performs offline deterministic evaluations. `templates/marketing/benchmarks` contains real authored devShark question/task and DNESKAi held article packets with original unavailable eligibility. The actual task fixture lacks an authored explanation but supports challenge-only rendering; its unverified source eligibility still holds production admission. Synthetic fixtures exist only in tests. `writeBenchmarkExamples(existingDatasetId, results)` can export hashes/QA codes to an existing EU dataset, with no source or copy text. It has not been invoked; the owner configures dataset scope, retention and access before a pilot.

### Owner feedback

`recordMarketingOwnerFeedback` (`owner-feedback.ts`) runs after approve, return, skip and edit in `POST /api/marketing/revisions`. It walks the decided revision's `replaces_id` chain back to the generated revision: the owner's rows only, the same trace, every stored hash rechecked, at most 20 saves. It then sends one `owner-review` feedback to that generation's trace, after the trace's own revision UUID and hash have been checked:

| Decision | score | value | `sourceInfo` |
| --- | --- | --- | --- |
| approved, no edits | 1 | `approved` | reviewed and generated revision ids and hashes, `edit_kinds: {}`, `edit_count: 0` |
| approved after edits | 0.5 | `approved` | the same, with the chain's edit kinds |
| returned | 0 | `returned` | the same |
| skipped | 0 | `skipped` | the same, and `reason: "skip"` |

An edit sends `owner-edit` without a score, with the kinds of that save alone. Edit kinds (`owner-edits.ts`) are counts per kind: `text-headline`; `text-body` (a body, kicker, credit or alt text, per field); `caption`; `image-swap`; `crop` (the same picture with another crop); `reorder` (the fewest moves); `remove-slide`; `schedule`. The stored decks keep no edit indexes, so slides are matched by type, variant and image slots with the fewest field changes. The feedback id is derived from the key, the decision and the revision id and hash, so a repeated decision cannot add a record under a second id. The owner's free-text note stays in OwnDashboard.

Feedback binds only to a hash the trace itself recorded. If LangSmith was down while a post rendered, its root keeps the hash from before rendering, and every later decision on that post is dropped as `trace-revision-mismatch`: no feedback rather than feedback on a hash the trace cannot prove. A post approved, then edited and approved again, carries one `owner-review` per decided revision on the same trace, because each revision hash has its own feedback id. Anything that aggregates these scores takes the latest `owner-review` per trace.

### Owner-edits evaluation set

`scripts/langsmith-owner-edits.ts` builds the evaluation set from the owner's decisions. Bundle it into the git-ignored `work/` and run it under the `react-server` condition, which turns the `server-only` marker into an empty module outside Next.js:

```bash
npx esbuild scripts/langsmith-owner-edits.ts --bundle --platform=node --packages=external --format=cjs --outfile=work/langsmith-owner-edits.cjs
export NEXT_PUBLIC_SUPABASE_URL=… SUPABASE_SERVICE_ROLE_KEY=… DASHBOARD_OWNER_ID=<auth user uuid>
node --conditions=react-server work/langsmith-owner-edits.cjs --dry      # counts only, writes nothing
node --conditions=react-server work/langsmith-owner-edits.cjs            # work/langsmith/dneskai-owner-edits-<date>.jsonl
LANGSMITH_API_KEY=… LANGSMITH_ENDPOINT=https://eu.api.smith.langchain.com \
  node --conditions=react-server work/langsmith-owner-edits.cjs --no-text --upload
```

It reads the owner's DNESKAi `marketing_revisions` with the service role and only selects. A revision is decided when it is approved (its `approved_hash` equals its content hash, also after publication), returned or skipped. Each JSONL line holds the example below and, unless `--no-text`, the generated and the decided title, caption and slide text, so the edits can be read side by side on this machine. `--dry` prints the decisions, the share approved without edits, the mean score, the edit kinds, the models and the skipped rows, and writes nothing. `--fixture rows.json` reads exported rows instead of Supabase. An existing output file is never overwritten.

Nothing leaves the machine without `--upload`. With it, the `dneskai-owner-edits` dataset in the EU workspace is created when missing, and each example is created or updated by an id derived from the decision and the revision hash. Inputs: `generated_revision_hash`, `model`, `prompt_version_hash`. Outputs: `revision_hash`, `decision`, `score`, `edit_kinds`, `edit_count`, `chain_length`, `caption_length_delta`, `slide_text_length_delta`. Metadata: `trace_id`. No text. The upload uses its own EU client with a 15-second request timeout, still without retries, and gives up after 60 seconds in total; a run that stopped part-way is safe to repeat, because the example ids do not change. A chain the script cannot prove (a missing parent, a hash mismatch, more than 20 saves) is counted as skipped, never guessed; owner-authored and imported revisions name no Claude model and are skipped as `not-generated`.

For interactive trace review, the owner can connect LangSmith's MCP server to Claude Code with their own EU key, in their own Claude Code configuration. It reads traces, feedback and datasets from the terminal; the production path never uses it, and no key or MCP configuration belongs in this repository.

### Model A/B evaluation

After 20 approved posts, compare Claude Sonnet 5.5 with Claude Haiku 5.5 offline on the same saved briefs, with nothing published:

```bash
npx esbuild scripts/dneskai-model-ab.ts --bundle --platform=node --packages=external --format=cjs --outfile=work/dneskai-model-ab.cjs
node --conditions=react-server work/dneskai-model-ab.cjs --briefs work/briefs.json          # dry plan, no model call
MARKETING_AI_CONSENT=true ANTHROPIC_API_KEY=… \
  node --conditions=react-server work/dneskai-model-ab.cjs --briefs work/briefs.json --live --media-dir work/media
```

`--briefs` is a local JSON export: an array of briefs, of `marketing_dneskai_briefs` rows with their `brief`, or `{ "briefs": [...] }`. `--media-dir` holds the brief's source pictures named by their sha256; each is checked against its name when loaded. Defaults: model A `claude-sonnet-5-5` at 2/10 USD and model B `claude-haiku-5-5` at 0.10/0.50 USD per million input/output tokens (the Claude API list prices of 6 October 2026; pass `--price-a`/`--price-b` when they change or for another model), 20 briefs (`--limit`), and a 1.00 USD ceiling that `--ceiling-usd` can only lower.

The dry plan builds the exact prompt the worker sends (`marketing-copy/7`) for each brief and prints per model the expected cost (one accepted attempt, prompt bytes ÷ 3 as tokens, 1,500 output tokens), the cost with one retry, and the worst case generation reserves (one token per byte, 2,500 output tokens, two attempts, at most 0.13 USD per job), with how many briefs fit one ceiling day. On 20 copies of a test brief of about 4,400 estimated input tokens it printed: Sonnet 5.5 expected 0.48 USD, worst case 2.26 USD; Haiku 5.5 expected 0.02 USD, worst case 0.11 USD; eight briefs per 1.00 USD day at the worst case, so three days for all 20.

`--live` runs `generateMarketingDraft` with the real studio fit gate, as the worker does, at each brief's observation time, for model A and then model B. A brief starts only while the run's reserved worst case for both models stays within the ceiling; the run then stops at `ceiling-reached` rather than give one model a brief the other never saw. Nothing is published, stored in Supabase or traced. This spend is not counted in `marketing_dneskai_generation_spent`, so run it on a day production does not need its ceiling, or lower `--ceiling-usd` by what production spent that day. The result file (`work/dneskai-model-ab-<date>.json`) holds per model the drafts produced, the retries, the retries caused by `text-clipped`, the mean attempts and the cost, and every draft for reading side by side. The share approved without edits needs the owner: read the drafts, and compare with the owner-edits set of the production model.

Result: not run yet. It waits for 20 approved posts and the owner's go for a live run of at most 1.00 USD.

### Brief input sizing

Brief prompts use a planning estimate of two UTF-8 bytes per token plus 2,048 tokens for schema/envelope overhead; the model A/B script uses a less conservative bytes/3 estimate. Neither is a tokenizer measurement. The offer shrinks excerpts and then sources/images to fit. Dollar admission remains byte-based, each paid call still reserves the existing job maximum, and reported usage must remain within the unchanged 20,000 input-token ceiling. No counting request or model call is made while preparing the offer.
