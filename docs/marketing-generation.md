# Marketing generation and rendering

This server-only marketing workflow accepts public authored source packets after the owner enables marketing-source consent. It sends their content to Claude. It never sends OwnDashboard project notes, contacts, invoices, financial records, learner responses, hidden grading tests or server solutions. The existing non-marketing no-model-call boundary still applies. No model or LangSmith network call ran during implementation.

## Bounded generation

`src/lib/marketing/generation.ts` exports `generateMarketingDraft(input, dependencies)`. Input includes a strict `SourcePacket`, account, schedule, template version, revision UUID, up to eight brand-matching presentation references and `consent: true`. Dependencies supply a configured `MarketingModel`, optional tracer/abort signal/clock, and a validated budget. The worker verifies source eligibility, expiry, brand/locale, content hash and a future schedule before provider admission. An Instagram reference can inform presentation; it cannot replace an article or exercise source.

`createClaudeMarketingModel({apiKey, model, pricing})` uses server TypeScript LangChain `ChatAnthropic`, forced strict structured output, temperature zero and SDK retries disabled. Configure the Claude model ID and current input/output token rates in the worker. Verify model access with the owner-approved pilot; implementation does not infer account availability or replace the configured model with a newer one. The documented Sonnet 4.6 standard rate at research time was $3 input / $15 output per million tokens; this is a setup reference, not a live billing feed.

The default budget allows two attempts, at most 20,000 reserved input tokens and 2,500 output tokens per attempt, $0.25 total estimated cost and 60 seconds for generation. A 60-second HTTP host should choose a shorter generation limit to leave time for rendering, uploads, source refresh and diagnostics. The reservation uses UTF-8 prompt/schema bytes plus envelope headroom. It is conservative admission arithmetic; billing reconciliation uses actual provider usage. No prompt caching, browsing, model tools, fallback provider or LLM judge participates.

Only known usage with invalid copy permits another attempt within the remaining reservation. Unknown usage, transport errors and provider failures stop without a retry because billing may already have happened. The durable runner must record provider admission before calling the model and reconcile a crash after admission rather than replay it.

Zod rejects schema drift and additional fields. Deterministic QA checks locale, unsupported URLs/HTML/control characters/emoji, novel numeric strings, evidence indices and missing article citations. Those checks do not prove semantic entailment or language quality. The owner reviews factual claims, natural Czech/English and evidence before approving the exact final revision hash.

For devShark the renderer receives original authored question text, option order, answer, explanation and exact source code. It never reconstructs these from model output. It removes recognized Markdown emphasis markers from displayed authored prose and moves a matching fenced code block into the exact-code slide; a mismatch holds the job. A coding task without a safe authored explanation becomes a challenge-only carousel: complete measured public spec, exact starter code and fixed CTA/caption. Model-written solutions and claims are discarded; overflow holds before a provider call. The model supplies title/caption for review; generated code is forbidden. DNESKAi copy remains Czech and links the exact article/evidence revision. devShark remains English. A final caption includes the canonical source URL; Threads captions exceeding 500 characters hold the draft.

## Humanizer in the structured generation call

The owner-requested [Humanizer skill](https://github.com/blader/humanizer/tree/225a6f39ac85f76ee48dbad772ea4abe4ed6c9d8) is pinned at commit `225a6f39ac85f76ee48dbad772ea4abe4ed6c9d8`, version `3.1.0`, MIT. `templates/marketing/humanizer/SKILL.md` and `LICENSE` preserve upstream bytes verbatim; `provenance.json` records their hashes, size, license, adaptation scope and source sections. This is a repository-local integration, with no global plugin installation.

`src/lib/marketing/humanizer.ts` derives `marketing-humanizer/1` from the upstream embedded editing mode. It supplies at most 2,500 UTF-8 bytes of instructions per call, rather than transmitting the full 32,348-byte skill. The adapter fingerprints its version, exact upstream commit/skill hash, review instructions and both language voices with `MARKETING_HUMANIZER_POLICY_FINGERPRINT`. Every actual generation system prompt includes that fingerprint and provenance. `marketing-copy/3` marks the changed generation prompt; older revisions and approvals retain their stored versions.

Within the existing Claude structured-output call, the model drafts, reviews and rewrites generated prose before returning only the final schema. The instructions ask for natural Czech reporting for DNESKAi and plain English for devShark. They remove staged hooks, hype, forced triads, repeated summaries, decorative labels and habitual dashes while preserving selected supported facts, scope, uncertainty, attribution and evidence indexes. They prohibit invented first-person experience, reactions, quotes and expert authority. This factual workflow narrows upstream voice matching and creative reactions: reference text cannot override the source or safety rules.

Only generated titles/captions and generated article slide prose receive style review. The server still supplies authored exercise text/options/answer/explanation/code and the full challenge specification; Humanizer cannot rewrite them or invent a solution. Challenge-only title, caption and CTA remain deterministic. The model response then passes the existing strict-schema/source/cost/QA gates, followed by rendering, source revalidation, hashing and separate owner approval. No second rewriting call, model judge, provider/key change, new tools or larger budget is added. Adapter bytes count toward the existing conservative input reservation, so a source exceeding that unchanged cap remains held.

Focused offline tests verify verbatim provenance, bounded instructions in the actual invocation for both brands, one-call valid drafts, unchanged usage/cost arithmetic, immutable authored exercises/challenges, existing fabricated-number/schema refusals, and consent/source/admission holds before invocation. Those tests make zero provider calls. Style instructions do not prove human quality or general factual entailment; the owner still reviews the exact final prose and evidence before approving its hash.

## DNESKAi slides: the vendored carousel studio

Since #117, DNESKAi has no layout of its own in this repository. Every DNESKAi slide renders through `renderDneskaiSlide` in `@boardlessai/carousel-studio`, the Design Lab engine from Quorum (quorum#603), vendored as built output in `vendor/carousel-studio/` and installed as `"@boardlessai/carousel-studio": "file:vendor/carousel-studio"`. The single-layout template `dneskai-editorial/2` (Claude Design, never approved), its derived layout and its brand and logo copies are deleted, and the staging approval receipt accepts devShark entries only. A DNESKAi entry in `MARKETING_PILOT_TEMPLATE_APPROVALS` now fails the whole receipt closed.

`src/lib/marketing/dneskai-render.ts` implements the `RenderDneskaiDeck` port from `dneskai-ports.ts` through `createDneskaiDeckRenderer({ storage })`:

- Each `DneskaiSlide` (`dneskai-slides.ts`) maps to the studio input: type, variant, words, `sources`, the photographs loaded with `loadMedia(assetSha256)` together with their crop, the slide's place in the deck (`{ index, count }`) and locale `cs`. The studio writes the folio, the sources title and the disclosure. A photograph used on several slides is loaded once per deck.
- The gate is the studio's plus three rules, so that the copy the owner approves is the copy that prints, whole and legible:
  - `text-clipped`, which the studio only reports, refuses here: cut Czech copy never ships. A slot the renderer cut without the studio reporting it refuses the same way.
  - `unsupported-glyph`: every drawn field is checked, as the studio draws it (trimmed, NFC, the kicker uppercased in Czech), against the committed face it is set in: headline in Space Grotesk 700, body and source lines in Source Serif 4 400, kicker and credit in IBM Plex Mono 400. The studio's DNESKAi API draws a character its faces lack as an empty box, or in another face, and reports nothing; an emoji, CJK or ✓ refuses the deck and the message names each character with its code point. The check reads the studio's own metric tables through the `./fonts` subpath (`resolveFace`, `missingCommittedGlyphs`), which are also what its fitter measures by. They cover Latin-1, Latin Extended-A and the common punctuation, including „ “ – — … × § %, but not U+201A ‚ (the Czech nested opening quote), ≥ ≤ ← ↗ ✓ • ™ π Ω.
  - `text-unplaced`: written text the slide type does not draw. The studio fills only its template's slots, so this text would sit in the approved deck and never reach the picture. Cover photo draws headline, kicker and credit; figure headline, body and credit; split and single headline, body, kicker and credit; statement headline and body; sources only its source lines. Blank text is no text.

  `tests/lib/carousel-studio-vendor.test.ts` derives the face and the placed fields of every vendored DNESKAi template from the studio itself and fails when `DNESKAI_FIELD_FACES` or `DNESKAI_PLACED_FIELDS` disagree, so a re-vendor cannot move a field unnoticed. Missing or undecodable photographs, a full-bleed photograph whose shorter side is under 900 px or whose crop stretches it more than 1.5×, a bad crop and a loader failure (`media-asset-unavailable`) refuse as well; a loader failure after the job's deadline is `worker-timeout` instead. One blocking problem on any slide refuses the whole deck, returns every problem with its slide, code, field and message, and stores nothing. When the text gate refuses, the remaining slides are validated, not drawn. `image-upscaled` renders and is reported.
- Each slide becomes a baseline JPEG: exactly 1080 × 1350, quality 92, 4:4:4 chroma, sRGB with an embedded sRGB profile, at most 8 MiB. The encoder output is read back and checked before upload.
- Assets come back in slide order in `AssetSchema` shape with the slide's alt text, together with each slide's render key.

`validateDneskaiDeck(deck, loadMedia, signal?)` returns the same problems, the text gate included, without rendering or storing anything; generation (#116) uses it to fit copy.

### Render cache

A slide's render key is `sha256(canonicalJson(…))` over the vendored engine (version, Quorum commit and tree hash), OwnDashboard's render policy (`dneskai-render/2` since the glyph and placement gates; every `/1` object is re-keyed and rendered once more), the encoder (sharp and libvips versions plus the JPEG settings), the words as the studio takes them (trimmed, blank source lines dropped), the variant, every photograph's asset hash and crop, and the slide's position. The studio's template choice and payload are pure functions of exactly these inputs, so the key hashes the inputs and a cache hit loads and decodes no photograph. The alt text is not drawn and is not part of the key. The key deliberately differs from the issue's `templateSha, payload, assetSha256[], focal[]`: under a pinned vendored tree the two are equivalent, and keying the inputs lets a hit skip the photographs.

`createDneskaiSlideStorage(db, owner)` in `worker-runtime.ts` keeps one immutable object per owner and key at `<owner>/marketing/dneskai/slides/<renderKey>.jpg` in the private `marketing-assets` bucket. It shares the devShark upload path: private-bucket check, `upsert: false`, size, type and metadata check, re-download with a sha256 comparison, then a seven-day signed URL. `find` verifies the stored bytes against the recorded sha256 before it signs; a tampered or foreign object fails instead of being replaced. Metadata records the owner, render key, JPEG sha256, renderer version and policy, studio template id and version, PNG and SVG hashes and any non-blocking problems, so a cache hit reports what the original render reported. Nothing revision-specific goes into an object, which is what lets every revision that draws the same slide reuse it. An unchanged deck therefore loads, renders and uploads nothing; editing one slide re-renders that slide only; an engine, policy or encoder change re-renders each slide once.

### Worker routing

`runMarketingWorkerJob` sends a DNESKAi Instagram draft to the deck renderer only when the draft carries a deck (generation v5, #116, attaches it). A DNESKAi draft without one fails with `dneskai-deck-required`; there is no layout fallback. `executeMarketingJob` binds the default renderer to the job owner and to `loadDneskaiMedia`, the stored-media loader from #114. Without a loader the job fails with `dneskai-renderer-unavailable`, and it fails before the paid generation, not after it (`assertDneskaiRendererAvailable`). A refused deck fails the job with `dneskai-render-refused`: the per-slide problems travel on the `MarketingRenderError` and `executeMarketingJob` returns them, at most 40 in the renderer's shape, as `problems` beside `errorCode`. The job row still stores only the code; persisting the problems for the review UI belongs to #118 and #119. DNESKAi jobs cannot be admitted yet: the legacy job template schema is devShark-only, and #116 defines the DNESKAi job.

### Updating the vendored studio

`vendor/carousel-studio/UPSTREAM.md` pins the Quorum commit and the tree hash and lists what was copied and why. Never edit the vendored files. `scripts/vendor-carousel-studio.sh check` verifies the tree; `scripts/vendor-carousel-studio.sh <quorum-checkout> <commit>` rebuilds a commit from `git archive` in a scratch directory and proves it equals the committed tree; adding `--write` replaces the tree and updates the commit, commit date, vendored date and tree hash in `UPSTREAM.md`. Then update `DNESKAI_STUDIO` in `dneskai-render.ts` (the vendor test fails until the commit and tree hash agree) and run `tests/lib/carousel-studio-vendor.test.ts` and `tests/lib/marketing-dneskai-render.test.ts`. The vendor test also reproduces all ten pinned DNESKAi golden PNG hashes with OwnDashboard's own sharp 0.35.5 and zod 4.6.7; npm dedupes both, and resvg 2.6.2, into one copy because the trimmed manifest widens upstream's exact pins to caret ranges.

## Deterministic JPEG rendering and storage (devShark)

`renderMarketingPreview(input)` allows local review of pending templates and rejects production environments. `renderMarketingAssets(input, storage)` requires a trusted Design-approved template. Instagram emits 1080 × 1350 JPEG slides, quality 92 with 4:4:4 chroma sampling, at most five slides and 8 MiB per JPEG. The renderer uses explicit pinned font files with system fonts disabled and validates original asset/font checksums.

Text fitting uses measured glyph advances, normalizes displayed prose to NFC, supports Czech diacritics, and fails on missing glyphs, long unbreakable words or vertical overflow. It preserves source-code identifiers, indentation and line breaks; code never wraps, truncates or normalizes Unicode identifiers. Unsupported code glyphs hold the render. A conservative collision gate also holds text that would overlap a surfacing fin. An overflowing exercise holds the job for an edited source/layout. It never creates a guessed replacement or fake product screen.

`MarketingAssetStorage.put({key, bytes, sha256, contentType, metadata})` returns `{url, sha256}`. The adapter must enforce owner-scoped storage, immutable object keys, no overwrite, and HTTPS access to exact JPEG bytes. The renderer rejects a returned hash differing from its local bytes. Metadata records revision UUID, template/export hashes, SVG hash and renderer version. Private storage with signed URLs is supported only when those URLs remain usable through the schedule and publication retries. Renewing a signed URL after re-verifying the bytes keeps the revision and its approval, because the approval hash excludes delivery URLs; see [DNESKAi revisions with media and crop](marketing-revision-media.md). Clean partial uploads after failed jobs with a retention policy.

Threads jobs skip rendering and retain a caption of at most 500 characters with an empty asset list. Store the final `ContentRevision` with its assets alongside the slide JSON. Hash the full final revision, including assets/account/schedule, before review. Source retirement, source supersession, changed assets, changed schedule or changed template requires a new revision and approval.

## LangSmith EU diagnostics

`createMarketingTracer` uses the explicit LangSmith SDK with `https://eu.api.smith.langchain.com` and EU web links. Configure an EU workspace/key; a hostname alone does not migrate a US workspace. Global LangChain/LangSmith tracing and verbose console tracing must remain disabled. The model call also runs inside a disabled traceable context. Native n8n workflow tracing does not represent this worker.

The adapter hides inputs/outputs, filters metadata, disables runtime/environment metadata, prompt cache and debug logs, and uses one-second diagnostic transport timeouts with no retry. It records source ID/revision hashes, exact source content hash, stored revision UUID, model, hashed prompt/template versions, knowledge UUIDs, attempts, latency, token usage, estimated cost and bounded QA codes. Raw source/copy, URLs, credentials, owner notes and exception text do not enter traces. Resolve the source ID/revision hashes against OwnDashboard's stored source records.

`recordPreparedRevision` adds render latency, asset hashes and the final revision hash to the same trace after source revalidation. `recordOwnerFeedback` verifies the trace's exact revision UUID/hash before sending an approval/returned/skipped decision and quality score. Free-text owner feedback remains local. The adapter returns private EU trace links and never enables public sharing. Diagnostics failures return false/null so they cannot authorize or block a draft. A missing trace means diagnostics are unavailable.

`generation-benchmark.ts` performs offline deterministic evaluations. `templates/marketing/benchmarks` contains real authored devShark question/task and DNESKAi held article packets with original unavailable eligibility. The actual task fixture lacks an authored explanation but supports challenge-only rendering; its unverified source eligibility still holds production admission. Synthetic fixtures exist only in tests. `writeBenchmarkExamples(existingDatasetId, results)` can export hashes/QA codes to an existing EU dataset, with no source or copy text. It has not been invoked; the owner configures dataset scope, retention and access before a pilot.

## Worker integration and verification

`services/marketing-worker/protocol.ts` exposes authenticated HTTP admission/status and a separate durable runner. Its README defines idempotency, owner scoping, fencing, source refresh, reconciliation and hosting requirements. n8n Cloud calls HTTP; it does not use Execute Command. Root API/DB adapters supply the durable queue, trusted template registry, storage and model configuration. This module provisions no hosting, paid service or production activation.

Focused tests cover consent/hash/eligibility isolation, references, immutable exercise semantics, retries/cost, article QA, Czech glyphs, overflow, reproducible JPEG bytes, pending template refusal, both-brand held benchmarks, EU redaction, final asset binding and typed feedback. Owner-approved read-only checks verified Claude model-list access and EU LangSmith project-list access on13 October2026. A separately labelled `connectivity-check` diagnostic through this tracer was stored/read in EU with absent inputs/outputs, hash-only source identity and zero model attempts/tokens; immediate read returned404 before indexing, and later read-only retrieval succeeded without repeat writing. No model was invoked. Live model quality, complete pilot trace/feedback binding, owner approval of the Design-derived templates, current eligible production packets, deployed worker limits and signed-URL lifetime remain owner-pilot/setup gates.
