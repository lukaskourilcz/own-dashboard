# Marketing integration contract v1

Canonical runtime definitions: `src/lib/marketing/contracts.ts`. Producers emit `marketing-source/1`; prepared posts use `marketing-content/1`; portable owner decisions use `marketing-approval/1`; publication records use `marketing-publication/1`. Matching JSON Schema exports are `contracts/marketing-source-v1.schema.json`, `marketing-content-v1.schema.json`, `marketing-approval-v1.schema.json` and `marketing-publication-v1.schema.json`. Unknown fields and versions are rejected. These records never carry owner IDs, user records, credentials or hidden grading tests. The authenticated integration determines the owner on the receiving server.

Source packet fields: `schemaVersion`, `brand` (`dneskai`/`devshark`), `kind` (`article`/`question`/`coding-task`/`instagram-reference`), `sourceId`, `sourceRevision`, `contentHash` (lowercase SHA-256), `canonicalUrl` (HTTPS), `locale`, `observedAt` (ISO with offset), `expiresAt` (ISO or null), `eligible`, `eligibilityReason`, `content`.

Content fields: `title`, `body`, `category`, `difficulty` (string/null), `code` (string/null), `options` (array), `answer` (string/null), `explanation` (string/null), `evidence` (array), `image` (object/null). Evidence has `url`, `title`, `excerpt`, `checkedAt`, optional `timecodeSeconds`. Image has `url`, `alt`, `licence`. All fields other than timecode are required; use explicit null/empty arrays when inapplicable.

DNESKAi: kind article, locale cs, actual BoardlessAI selected article revision and citations. devShark: kind question/coding-task, locale en, effective current bank plus DB overrides and active eligibility. A question carries authored options, answer and explanation. A coding task carries its public specification, examples and exact starter code; its authored explanation may be null. Without an explanation, consumers produce challenge-only slides with a deterministic authored title and task-link caption, never a solution, hidden tests or server answers. An unavailable effective source yields a held/error result, never an invented eligible packet.

`contentHash` hashes the `content` object only using SHA-256 UTF-8 canonical JSON: recursively sort object keys lexically; preserve array order and string bytes; no whitespace. `sourceRevision` identifies the full version including eligibility changes. Consumers verify hashes. A tombstone uses the same source ID, a new revision, `eligible=false`; retain content or the last safe authored version so it still validates. Consumers invalidate unposted dependent revisions on supersession/retirement.

Receiver: authenticated POST `/api/marketing/automation` body `{action:"source",packet:<SourcePacket>}`. Headers: Bearer integration secret, `X-Marketing-Timestamp` unix seconds, `X-Marketing-Signature` lowercase HMAC-SHA256 over `<timestamp>.<exact raw UTF-8 request body>`. Each producer gets its own secret bound server-side to a fixed brand/owner. A callback without valid signature, with wrong brand or more than five minutes old is refused. Replay suppression is keyed by source identity/revision/hash. Production endpoints and secret provisioning are setup actions, not included credentials.

OwnDashboard retains content revisions, approvals and publication records. The owner approves the exact hash of the full prepared revision, including asset hashes, account and scheduled time. Replacing a revision invalidates the prior approval. Sources are checked again before publication. Drafts without final assets cannot be approved for Instagram.

`ApprovalDecisionSchema` contains `schemaVersion`, `revisionId` (UUID), `revisionHash` (lowercase SHA-256), `decision` (`approved`/`returned`/`skipped`), `decidedAt` (ISO timestamp with offset) and `feedback` (string up to 2,000 characters or null). Hash the complete final `ContentRevision` using `revisionHash` from `src/lib/marketing/hashes.ts`, including exact asset hashes, alt text, caption, source references, account and schedule. `parseApprovalDecision(value, {revisionId, revisionHash})` rejects another revision or a stale hash. Derive the expected binding from the owner-scoped stored revision, never from fields supplied alongside the decision. A schema-valid record does not grant consent or authorization: the authenticated owner and atomic current-state approval gate remain required. Article approval, account verification, template approval and campaign activation cannot approve a social revision.

`PublicationReceiptSchema` contains `schemaVersion`, `publicationId` (UUID), `revisionId` (UUID), `revisionHash`, `platform` (`instagram`/`threads`), `observedAt` (ISO timestamp with offset), `status`, `remoteContainerId`, `remoteMediaId`, `remoteUrl` and `errorCode`. Nullable fields must be explicit. Remote IDs contain no whitespace and are bounded to 200 characters; error codes are lowercase letters, digits and hyphens, bounded to 100 characters. HTTPS public links are bounded to 2,048 characters and cannot embed credentials. These are per-channel records; one channel's published receipt does not imply another channel succeeded.

| Status | Remote evidence | Error |
| --- | --- | --- |
| `queued` | All remote fields null | Null |
| `claimed` | Container or durable intent may be known; media and URL null | Null or bounded code |
| `published` | Nonempty media ID and valid public HTTPS URL required; container nullable | Null |
| `failed` | Container may be retained; media and URL null | Required bounded code |
| `reconciliation` | Container and known media may be retained; URL requires a known media ID and may remain null | Required bounded code |
| `cancelled` | All remote fields null | Null or bounded code |

`parsePublicationReceipt(value, {publicationId, revisionId, revisionHash, platform})` checks every binding against owner-scoped stored state. Schema validation cannot authorize a state transition or prove that a remote post exists. Persist receipts with the current publication fence and atomic revision transition. A timeout, missing permalink or lost response stays in reconciliation; retain known media/container evidence and query it instead of posting again. A queued, claimed, failed or cancelled record cannot claim published media. Publication additionally requires the exact current approval, enabled verified account, due slot and live producer recheck (last source observation within 15 minutes).

These portable schemas are additive exports for shared integrations. Existing HTTP action envelopes remain unchanged: owner approval uses `/api/marketing/revisions` `{action:"approve",id,expectedHash}`, and signed automation source ingress uses the source envelope above. The current automation route only receives source/revision writes; legacy external publisher claim/receipt actions are refused. `/api/marketing/n8n` orchestrates bounded native operations with a fixed owner credential. The shared record parsers do not replace authentication, ownership checks, the durable queue or database fencing.

Contract tests compare all four JSON exports to their Zod definitions and exercise exact revision binding, malformed UUID/hash/time, required published evidence, ambiguous receipts and unposted states. The retained real coding-task benchmark remains `eligible=false` with the expected `source-unavailable` hold; challenge-only layout support does not change producer eligibility.

Core pipeline uses n8n Cloud, Claude Design templates, bounded LangChain generation and LangSmith diagnostics. Dots and Higgsfield are excluded.
